---
name: dsh-host-build-restart-verify
description: "Build, load, and verify a dsh-project-context plugin change against the dsh host process that is actually serving the session (desktop vs web), including the restart and tab-reload steps and how to tell which code is live."
---

Use this whenever a change touches plugin host code (`src/**`, or anything that ends up in `lib/*.js`) or the client bundle and you need to reason about, or actually make, that change effective in the running dsh host.

1. A commit is never enough. The host loads plugin code from the repo's built `lib/*.js` through the profile `link:` dependency (e.g. `~/.dsh/profiles/web/package.json`). `pnpm test` / `pnpm typecheck` prove correctness, not that the host runs the new code.

2. Build before anything else. Node lives in the Nix store and both its path and its version rotate, so derive it — never paste a recorded store path (recorded ones have already gone dead):
   run `node -v` first, then `PATH="$(dirname "$(command -v node)"):$PATH" pnpm build`
   If `command -v node` is empty, find the store path yourself with `ls -d /nix/store/*nodejs-*/bin` — usable but ambiguous, it also matches `nodejs-slim-*-dev/-npm/-corepack/-source`, so pick a real `bin/node` (do not pick a version from a note).
   Client bundle changes also require `pnpm build` (`pnpm test` compiles the host only). Run `pnpm test` and `pnpm typecheck` in the same pass and read the count the run prints — never a recorded count (recorded baselines such as 145/145 and 132/132 both long outlived reality).

3. Identify which host is actually serving the session before proposing or checking a restart. `desktop` (electron, `127.0.0.1:19387`, profile `~/.dsh/profiles/desktop`), `web` (`127.0.0.1:3080`, profile `~/.dsh/profiles/web`) and `ctxdev` all mount these plugins. Check the listening socket and the serving process's PID and start time (`ps -o lstart= -p <pid>`); do not assume the newest commits are loaded and do not assume it is the 3080 server.

4. Compare the host start time against the **first build that carried the change**, not the newest `lib/` mtime. `tsc` rewrites every `lib/*.js` on any build — including one with no source change — so the newest mtime is routinely later than an older host start, and comparing against it reports a false "not loaded" (reproduced 2026-09-27: a no-src-change `pnpm test` moved `lib/` mtimes a day past the last `src/` commit, which the mtime rule would read as "the change is not live" even though nothing changed). The three-part check: last `src/` commit time < host start, and the change's characteristic line is present in `lib/` (`grep` it). The content-level form of that third part, which no mtime can fake, is to recompile the current `src/` into a temp dir and diff it file by file against `lib/` — `diff -rq <tmp> lib/` is byte-exact because `tsc` rewrites mtimes but not content. `lib/` mirrors `src/` as the same per-plugin directories (`lib/{project-context,project-memory,project-autolearn,project-handoff,shared}/*.js`) with **no** `lib/index.js`, so the only extra entry on the `lib/` side is `lib/client.js` (the client bundle, built by `scripts/build-client.mjs`, which `tsc` does not produce). Since 2026-10-05 `lib/` is **tracked**, which makes the same content check cheaper and repo-wide: build, then `git diff --exit-code -- lib` must be empty — a non-empty diff means the committed artifacts are stale relative to `src/`, and the running host is therefore not running what `src/` says.

5. **Loaded is not the same as effective.** Step 4 only proves the host is running the new bytes. For a behavioural change, close the loop on one real event the plugin must have produced, and prefer artifacts the plugin itself stamps — a host running old or inert code cannot produce them.

   For `project-handoff` (the `turn/end` trigger), a genuinely completed handoff leaves a three-part trail: the handoff document's own embedded timestamp (`.agents/memory/HANDOFF.md`, the `- 生成时间：…Z` line), the successor session (its `session/title` starts with `↪ handoff · <parent>`, cwd = project root, and its first user message is the plugin-generated continuation banner), and `~/.dsh/storages/workspace.json` listing the **parent** in `global.archivedSessionIds` (the retire step). Compare the successor's `createdAt` and the document's mtime against the parent log's last `turn/end` — the gap is the summary call.

   Rule out the manual path before crediting the automatic one: upstream `interaction/commands` appends `command/run` + `command/done` to the session log (`appendLifecycle`, log-only appends), so a parent log carrying neither, plus no user message containing `/handoff`, was not commanded. Read the parent log with `zstdcat <dir>/session.v4.jsonl.zstd` and count event **types** — never `grep` for the string `/handoff`, because the agent's own prose is in the log and dominates the count.

   Reconfirmed 2026-10-02: parent `4cdeb0b9` ended with `turn/end` at 22:06:45, `.agents/memory/HANDOFF.md` was stamped 22:06:54.017Z, the successor was created 22:06:54.019, and `workspace.json` was rewritten 22:06:55.220 with the parent archived — on a host started 22:02:11 from a `lib/` built 21:56.

6. **Place a "it did not take effect" report on the timeline before believing it.** Desktop boots on this host get interrupted by incompatible third-party plugins (`~/.config/@deepseek-ai/dsh-desktop/logs/crash-*-host.log`), so the pid that answers is not necessarily the one the user just launched, and an observation can predate the successful start. Check three things before diagnosing: the timestamp of the user's message; the current socket holder's start time (`ss -ltnp | grep 19387`, then `ps -o lstart= -p <pid>`); and whether the socket-holder pid is the same across three samples with no new `crash-*` log. On 2026-10-02 the user asked at 22:01:39 while the 22:00:37 boot had already failed and the replacement host only came up at 22:02:11 — the change had taken effect, and the automatic handoff fired on the first post-restart turn that did not end on a question.

7. Never restart the user's host unprompted. Propose the restart (naming the host, PID, start time, and the commits that would load) and wait — goal/session control belongs to the user's agent session.

8. After an authorized restart, hard-reload every open dsh tab (`Ctrl+Shift+R`, or open a fresh tab). The browser-session cookie in `~/.dsh/.credentials.yaml` (`client-connection/browser-session`) is created once and does not rotate on restart, so no re-auth is needed. Client-only bundle changes are live via HMR after `pnpm build`, but already-open tabs still need one hard reload.

9. If old tabs look normal after a restart but actions never reach the server (half-dead UI), close all old dsh tabs and open a fresh one — the reconnect backoff (0.5 s → 10 s cap) does not always recover. A new tab restores sending in the same process.

10. Report verification honestly: host PID and start time, build time, and the fact that start > build. If the restart has not happened, say the change is committed/built but not yet loaded. Remember that host-side behavior can only be checked through the running host (read-only RPC/`Cordis` probes or the user's browser); there is no Chromium/Playwright on this machine.
