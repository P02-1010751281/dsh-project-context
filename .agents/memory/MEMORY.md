## Memory cap and the loaded-memory trap
- `MAX_MEMORY_CHARS` 32000 (was 24000), `MIN_MEMORY_CHARS` 4000, limit 200000, configurable via `maxMemoryChars`. All `normalizeMemoryDocument` call sites take the limit（`src/` 现为 **6** 处；现查 `git grep -n 'normalizeMemoryDocument(' -- src/ | grep -v 'export function' | wc -l`）。
- A capped document is cut on a line boundary (`clipToLineBoundary`, never a bare slice) and gets a marker `_[memory truncated at <limit> characters: <dropped> dropped]_`. `isMemoryTruncated(text: string)` and `clipToLineBoundary` live in `src/project-memory/document.ts` (**takes the document string, not the `LoadedMemory` object**); `loadMemory(projectRoot, limit)` is **async** and returns `{text, source, poisoned, unreadable?, damaged?}` from `src/project-memory/load.ts`.

- Editing `MEMORY.md` with the edit tool bypasses the plugin write path；下一次插件写入会**静默丢掉超出部分**。**检查**：`wc -m`（**字符**；`wc -c` 是字节，CJK 文档会虚高约三分之一）+ `loadMemory(root, 32000)` + `isMemoryTruncated(loaded.text) === false`；**绝不用 grep 找 marker** 判断。**只记量级与轮次、不写死具体数字**。consolidation 只压**与权威副本重复的叙述**、历史 hash 链与陈旧断言；约定 / 不变量 / 已接受的残余清单 / 开放项指针一条不动。**交付线那些串是否还在本仓，现查** `git grep -oF <string> -- .`。

## Threshold design — dsh vs pi
- pi's `kneeTokens` 是拟合 MRCR 8-needle 总体数据的跨模型质量曲线：`round(W − (W − 157K) / (1 + e^(−ln(W/450K)/0.04)))`。目的是**不信声明窗口**。W ≲ 400K 时 `knee(W)` 已超过 `usable − SAFETY_MARGIN`，所以那里是容量而非曲线在约束。
- **dsh 的 knee 是回退链、不是上限**：`quality = upstreamUsableInput ?? knee(window)`，然后按 pi 的顺序 `threshold = min(max(baseline+keep+summarizeTokens, quality), usable − SAFETY_MARGIN)`（字段名是 pi 的 `summarizeTokens`）。
- **This is a behaviour change, not a no-op**: default `handoffTargetTokens` 64000 / baseline 6000 / keep 20000 now yields pi's documented `boundary` shares（**别把百分比与窗口错位配对**，现算 `threshold / W`）；旧的 90K 是 `baseline + keep + target`、根本没有质量层。
- **dsh exposes NO upstream usable-input field** (`LlmResolvedModelInfo.context` is only `{ contextWindow: number }`)——这是**真** seam；`qualityLimit(window, upstream?)` 是接线点，现在什么都不传，**不要伪造第一个分支**。`discovery.ts` (`capacity()` first-match-wins over five spellings) 是 dsh **core**，不是本仓。
- **`resolveThreshold` was split** into `handoffRoom` / `qualityLimit` / `capacityLimit` + 一个只选模式并组合它们的 orchestrator。It used to mix six jobs；`thresholdRefusal` 现在复用 `handoffRoom`。
- **跨计量基准相减曾让 auto 模式「结构上无阈值」（2026-09-27 发现，2026-10-02 修复）**：`floor` 原为 `max(0, totalTokens − surfaceTokens) + keep + MIN_SUMMARIZE`。dsh 的 meter 里 `totalTokens` 锚在 provider `usage`、`surfaceTokens` 是固定密度启发式（`estimate.ts` 的 `CHARS_PER_TOKEN = 4`），两个基准不同 ⇒ 差值是**真开销 + 密度误差**，且随中文字符数**线性增长**。**修法**：`floor` 不再相减，改读可选的 `ContextMeasurement.overheadTokens`，而信封**不是猜的**：`ctx.sessionProjections.snapshot(session, ['contextBreakdown'])`（token-meter 注册的 projection，`systemTokens + toolsTokens`＝信封；GUI 上下文面板读同一个）。`runtime.ts` 的 `projectionEnvelope`（缺失/畸形返回 `undefined`，不猜）+ `measuredContext`（auto 路径与 `/handoff status` 回执的**唯一**入口）。读数走 `ctx.get("sessionProjections")`。
- **`contextBreakdown` 是 `/4` 启发式**（`projection.ts` 自己写明：估计器系统性低估 CJK 文本与 JSON schema，这正是 provider 锚定的 `projectedTokens` 要把误差挡在占用率之外的原因），所以信封与 `keep`/`MIN_SUMMARIZE`/`handoffSplit` 同基准、floor 内部自洽，只剩 `tokens` 那一次比较仍是「窗口基准 vs 启发式」——**原设计如此**。若要把信封也做成 provider 精确，锚点是 `contextPressure.pressureTokens`（可做，当前不需要）。
- **信封的字段形状只能从源码验，不能从投影缓存验**：缓存行存的是 projection 的**状态**（`{nodes, breakdown}`），而 `sessionProjections.snapshot()` 返回的是它的 **wire view**＝`{systemTokens, toolsTokens, messageTokens}`（`breakdown-projection.ts` 的 `wire: { viewSchema: breakdownSchema, view: … }`；`session-projection/src/index.ts` 的 `snapshot()` 与冷读 `viewCheckpoint()` 都过 `view` + `viewSchema`）——`projectionEnvelope` 读的字段是对的，在缓存里看不到顶层 `systemTokens` **不是**缺陷。
- **回执现已点名「信封来自哪次读取」（2026-10-03 修，此前是盲区）**：`threshold auto <n>` 在信封读到与读不到时是**同一个字符串**（大窗口 + 小 `keep` 时膝会压过两种算出的 floor），所以 `contextBreakdown` 解析成功与否从回执里**不可证伪**。现在 `measuredContext` 一并返回 `envelopeSource`：`"projection"` = harness 的 `contextBreakdown`、`"meter"` = meter 自己给的同一个量，回执据此渲染 `harness envelope <n>` / `meter envelope <n> — not the harness composition` / `harness envelope unavailable — no contextBreakdown projection`。归因落在唯一入口上，所以不会「值对、出处错」。**别再把它当盲区、也别再用推算判它**——读回执即可。本机信封量级 ≈ 4.5 万，够不到膝。
- `quality-knee` **仍然可达**，但只剩用户自己那一条路：`handoffKeepTokens` 上界 200000（`config.ts`）。回执按「`keep` 能否清掉膝」分别给词——不能清时**不再**把 `keep` 说成杠杆。**「值不值得折」由 `auto.ts` 对真实 `handoffSplit` 比 `MIN_SUMMARIZE` 独占**。杠杆仍成立：`/handoff now` 两个闸都不查；`/handoff 0.4` 不过膝。**诊断别倒序**：两个守卫（pending question / 跑着的子代理）都排在阈值之后。
- **第二道闸（阈值修好后真正的拦截点）**：`handoffPendingQuestion` 默认 **`"defer"`**，`auto.ts` 在阈值之后立刻判「最后一条 assistant 消息是不是问句」，是就 `return`。agent 每轮以问句收尾时 auto 每次都被挡下；要它不挡就 `/handoff pending wait`。
- **会话级判据可以只读地推出来**：`meter.measure(session).totalTokens` 就是该会话日志里**最后一条 `assistant/message` 的 `data.usage.totalTokens`**，同一份日志的 `request/context` 给 `contextWindow`；再拿最后一条 assistant 文本是否以 `?`/`？` 收尾判第二道闸。**auto 只在 `turn/end` 评估、没有定时器**（`src/project-handoff/index.ts` 的 `session/event` 过滤器对非 `turn/end` 直接 `return`；`src/project-handoff/` 里无 `setInterval`/`setTimeout`）——所以一个已远超阈值却**不再结束回合**的会话**永远不会** auto 交接。auto 路径已被活体验证多次（含**链式**：由交接横幅开启的会话自己在末次 `turn/end` 上再交接）；后继的钉子一致：`session/title` = `↪ handoff · <父 id>`、首条 `user/message` 的 `source.kind` = `dsh-project-context`；**auto 与手动 `/handoff now` 的分野是父会话有没有 `command/run`**。**教训：判「这功能被活体验证过没有」要扫全部工作区，别只看被问的那两个**——修复前 auto 路径结构上不可能触发，所以那一次触发本身就是「修复已加载」的判据，而当时的交接文档却把它写成待办。逐次会话 id 与数值不在此枚举（`git log` 与会话日志现查）。
- **`handoffPendingQuestion` 是 profile 级的，会话属哪个 profile 在日志头里查不到**：desktop 与 web 的 `cordis.patch.yml` **都有** `project-context` 条目、都设 `handoffPendingQuestion: wait`，且都已把 `handoffKeepTokens: 0` 对齐（`keep: 0` = 只带摘要），两个 profile 在 handoff 三项上一致；默认值见 `src/shared/config.ts` 的 `DEFAULT_CONFIG`（`handoffAdaptive: true` / `handoffKeepTokens: 20000` / `handoffPendingQuestion: "defer"`）。bundle 层 `cordis.patch.yml` 只做 `insert`、**不带 config**，所以 profile 层补的键就是该行唯一的 config——而 `config` 是**整体替换、不深合并**，要补别的键就得一并重述。**四个插件共用同一个 settings namespace，键控在 Loader 的 `project-context` 条目上**：只有它导出 `PluginSettingsSchema`（每个字段都带 `volatile` 标记，否则 `describe()` 整条跳过、卡片**静默**消失），它 `apply` 时用 `publishProjectContextSettings` 发布自己解析后的 config，另三个经 `effectivePluginConfig(entry)` 读它、仅在 owner 尚未 apply 时回落到自己条目的 config（`src/shared/settings.ts`）。**陷阱**：把 handoff 的键写到 `id: project-handoff` 上会被**忽略**（`live?.() ?? fallback` 里 owner 的值优先）——别「顺手」挪条目。会话属哪个 profile 只能按「被哪个宿主打开」判定——**现查** `ss -ltnp | grep 19387`（desktop）与 3080（web），别沿用记录。

## Probe traps
- pi harness probes must pass `cwd`: `makePi({ cwd: tmp })`, else the exec stub returns `process.cwd()` and `getProjectRoot` searches the wrong directory.
- dsh's skill-log directory is `.agents/memory/session-logs` (`project-state.ts:111`)；fixtures elsewhere make `archivedSessionIds` empty, so every case is rejected by the evidence rule — a fabricated "all cases behave the same".
- `tsc` emits tagged templates as `String.raw` followed by the template **with a space**, so `grep -cF` for an in-template marker returns 0 and looks like a failed restore or an empty mutant; locate mutants with `grep -n "<NAME> = "` in `lib/`.
- Counts of "reachable states" are domain-dependent (24 / 84 / 170 / 12 / 1608 were all reproduced under different scan domains) — never cite a bare count; give the mechanism plus a named domain.
- A report whose metadata is wrong must not be cited as-is: re-verify a finding's path/line before acting on it. A commit message claiming a fix landed is not evidence — read the diff (2026-10-03: `fa454aa` claimed to fix a frontmatter it never touched).
- Probes in `/tmp` resolve relative imports against themselves — import host modules by absolute path.
- **会话日志里的字符串计数不可用**：日志会回显 agent 自己的命令输出，`grep -c` 数出来的「插件说了 N 次 X」大多是探针自身（本会话 `quality-knee` 386 次几乎全是 grep 输出）。要判活体行为，改走只读接口（`cordis_inspect_query` 的 `Config`/`Service`、投影缓存），别数日志字符串。
- **`/handoff status` 回执不自证身份**：`threshold auto`/`context` 是 profile + 模型级的数，跨工作区会一模一样（同为 1M 窗口 ⇒ `threshold auto 157000`），引用回执必须带工作区 + 会话 id。已发生过一次把它误记成「本项目会话的用户回执」——那条实为另一工作区某会话的读数，且从未进过 tracked 文件（用 `git log -S` 现查）。

## Conventions
- NEVER hand off, compact, or end a turn while a teammate is running——在飞的 teammate 随父回合一起死、工作丢失。它们是进程内的（`~/.dsh/sessions/` 没有条目），只显示 `provisioning → active`、没有终态。规则：`list_agents` + 等每个在跑的 teammate（或显式 interrupt）之后才能交接/压缩；对 inactive 成员 `send_message` 不可信；用重查 `list_agents`/`team_task_list` 确认；从 `/tmp` 抢救半成品而非盲目重开；要求每个 teammate 边做边把报告写到固定路径。
- A teammate that dies mid-mutation leaves `src/` dirty: snapshot `src/` (copy + `sha256sum`) into the task text before spawning, require the restore command in the report, and run `sha256sum -c` after every teammate settles or dies.
- An unvalidated mutant produces an invalid red. A valid mutant must (a) compile with 0 errors, (b) have its marker in `lib/` **after** `pnpm build`, (c) demonstrably change behaviour on a probe input. Restoring `src/` does NOT restore `lib/` — end a mutation round with a rebuild and marker count 0. Edit `src/` only, restore from a hash-verified `/tmp` copy, never via `git checkout --` or `git stash`.
- A heuristic wording classifier does not converge by patching — it trades one error class for another. When two rounds swap the same bug back and forth, you are missing a discriminator, not a pattern.
- **验证脚本必须自证工具面，且每条失败路径都要真的能到达**：`set -euo pipefail` 下 `x="$(grep … | head -1 | sed …)"` 的 grep 无命中会让脚本**在它自己的 fail 分支之前**退出。检出办法：对每条 `var="$(…)"` 问「它失败时，下一个读它的分支还到得了吗」。
- **改长行不要用「按前缀 replace」的脚本**：改写后要读回该行，并检查「同一句出现两次」。
- Memory stays concise (< 6000 words); no secrets, credentials, or generic advice; unresolved work lives in memory/context, not in skills.
- Do not touch the user's own dsh sessions; goal/session control belongs to the user's agent session. Read-only investigation of `~/.dsh` stores is fine (`zstdcat session.v3.jsonl.zstd`); throwaway probe sessions only under `/tmp`, archived afterwards.
- A second agent session may be working in this repo concurrently: stage only the files changed for the current task (`git add <paths>`, never `add -A`) and commit with `git commit -F <msg> -- <paths>`.
- Do not restart the user's `dsh web` service unprompted; propose the restart. 桌面端同理——先证明「已加载 / 未加载」，再问要不要重启。
- Fixes must be verified by probe/API check before implementation, not adopted from review prose. Each batch gets an independent adversarial review, and new tests are mutation-checked against their fix.
