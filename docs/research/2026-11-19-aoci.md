## 0. 结论

1. **AOCI 是「仓库级认知索引」，不是记忆系统、也不是压缩器。** 它让模型为每个受管对象（文件 / 数据库表）
   写一行 FRAS 条目：职责、强关系、对外契约、不可从代码推断的约束；程序负责治理（作用域、基线、漂移、
   事务、恢复），索引以纯文本进 Git，通过 stdio MCP 的九个工具读写。
2. **它回答的问题和我们不同，但抢同一份上下文预算。** 它答「这个代码库长什么样」，我们答「这个项目
   决定过什么、会话该在哪切断」。一份 700K 行系统的索引约 300K token（README 自述），这比本机
   `handoffThreshold 400000` 的交接线、比 157K 的质量膝线都更早把窗口吃掉——所以它是**抢占者**，
   不是可以顺手叠加的补丁。
3. **裁定建议：不作为运行依赖引入。** 三条硬冲突都在我们自己的不变量里：规模（索引 token 量级 vs
   我们的种子/注入预算）、依赖（Go 二进制 + MCP 服务器 + 每仓 1 小时/20 万行的初始化）、许可
   （FSL-1.1-MIT，source-available，不能随包分发）。
4. **值得借鉴的是它的「证明」与「词汇」，不是它的索引**：交付 attestation（chunk + cursor + challenge）、
   漂移分类（Missing / Orphan / Stale / Unbaselined）、`derived=true / authoritative=false` 的显式来源标记。
5. **一条反向证据**：AOCI 自己规定「已知压缩后必须重新加载规则 + 完整 Overview + attestation」，
   并且明说交付内容不能被压缩摘要保留。这正好印证我们 §9 的裁定——大块认知与压缩天然冲突，
   不该指望「被压缩后还能保真」。

## 2. 机制

### 2.1 三层结构

| 层 | 载体 | 谁写 |
|---|---|---|
| 协议 / 规则 | Root `aoci.txt` 声明参与的 Volume；Meta 存 tag 字典、FRAS 规则、配额、写作契约 | 程序（`init`）写，模型不自由改 |
| 条目 | Code Volume（每文件一行）、Database Volume（每表一行） | 模型写，程序治理后入库 |
| 治理状态 | `.aoci/`：ledger、draft、transaction、baseline、receipt、recovery | 程序写，默认不进 Git |

Root / Meta / 两个 Volume 合起来叫 **Whole-Index**。Root 最后发布——「部分资产不能被误认为完整集合」
是它的显式设计。Volumes v1 的识别是一条精确 marker（`#AOCI-ROOT-MANIFEST: 1`），缺 marker 按 legacy
单体布局读，marker 损坏则 **fail closed**，绝不猜。

### 2.2 条目格式：FRAS + 符号坐标

一行一条，四段：**F** 职责、**R** 强关系、**A** 对外接口、**S** 不可推断的约束；行首 `file.go[CG9L]`
是 tag 坐标（架构层 / 功能域 / 重要度 / 规模）。README 里给的真实条目（本仓库 Go 代码库的 `atomic.go`）：

```text
atomic.go[CG9L]: F:Provides durable replace CAS, create CAS, atomic writes, and no-clobber recovery moves |
R:code:internal/fs/atomic_exchange_linux.go,… | A:AtomicWrite,AtomicWriteCAS,… |
S:Native publication never degrades to an overwriting rename; on a race, unsafe type, or unverifiable bytes, preserve third-party state
```

两个设计细节值得记：

- **S 字段有准入规则**（`#S-Admission: non-inferable-and-error-preventing`）和**按重要度的字符配额**
  （如 `C9-8≤600 C7-4≤200 C3-1≤50`），且配额的权威是**二进制**不是项目文本
  （`#FRAS-v2-Limits-Authority: machine-contract`）——项目改不了自己的上限。这和我们「预算数字只有
  一个来源」的纪律同构。
- **文件级独立**：每条只依赖自己的源文件，跨文件关系靠 R 里的文件名引用，因此可以增量维护。

### 2.3 治理链

写作不是「模型改文件」，是一条事务链：**源绑定 → plan → 校验 → review → CAS → 同目录临时文件 →
平台原子替换 → Baseline → recovery**。作用域三角：`index`（进索引）/ `observe`（只观察变更）/
`exclude`（明确排除）。漂移分七类：Missing、Orphan、Stale、Unbaselined、行尾变化、curation 差异、
不参与写作的源（空 / 二进制 / 超大）。Volume 的 apply / Baseline / scope 投影是**一个事务结果**，
不允许「这个文件成功了、另一个 Volume 没基线」的半完成态。

### 2.4 交付与证明（最值得抄的一段）

新会话里模型读一次 **Overview**：start marker + 当前正式索引全文 + end marker。超额则分块：
chunk 1 立即交付，模型必须按 `next_cursor` 跟到最后一页，然后提交**一次 attestation**（挑战）。
规则很硬：

- 本地搜索、旧记忆、补读源码**都不能算作完整交付**；
- 已知宿主压缩后，必须重新加载规则、声明 `context_compaction` 新事件 id、走完一次完整的 Overview +
  确认 + attestation；`check_only` 不算；
- 压缩交接**不得保留或摘要**索引正文，只能留 receipt 身份、未完成的写/恢复状态、立即重载指令；
- 重载若再次被压缩，服务器返回 `delivery_mode=capacity_stop`，任务转为 source-bound 继续，**不许循环**。

状态是五维而不是一个布尔：`delivery_verified` / `model_cognition_usable` /
`strict_attestation_verified` / `governance_aligned` / `current_system_cognition_reliable`，且互不替代。

### 2.5 它明确不做的事

不是知识图谱（关系投影 `derived=true`、`authoritative=false`，删掉可重算）；不自动推断语义
（不从 import、SQL、文件名、相似度生成关系）；不碰业务数据（只读 catalog 元数据，DSN 只经环境变量名，
MariaDB 直接拒绝）；不替代 RAG / LSP / 调用图（它自称「global semantic prior」，精确证据仍靠源码与图）。

## 4. 与本仓库的关系

| 维度 | AOCI | 本仓库 |
|---|---|---|
| 作用对象 | 代码结构 + 数据库 schema | 项目事实、决策、会话边界 |
| 载体 | `aoci*.txt`（每文件一行） | `MEMORY.md` 四节 + `CONTEXT.md` / `tasks/*.md` + 归档 |
| 权威源 | Git 里的 Volume + `.aoci` Baseline | 追加式 `memory.jsonl` |
| 写作 | 模型写、程序 plan/CAS/原子写 | 模型写、程序 tier C 整次拒绝（字节不变） |
| 时间性 | 与**代码版本**对齐（漂移检测） | 与**会话**对齐（turn/end、退休、交接） |
| 读入 | MCP 工具按需拉取 + Overview 证明 | 每轮 `systemPrompt.context` 注入（同步纯读） |
| 失败模式 | 索引漂移 / 未 attest | 有损整理 / 静默丢条（已用整次拒绝堵住） |
| 分发 | 单二进制 + stdio MCP | 纯插件，无服务器、无二进制 |
| 规模感 | 300K token 量级 | MEMORY.md 实测 44,996 字符（cap 45,000）+ CONTEXT 3,119 字符 |

**共同点比差异更值得注意**：两边都是「模型写文本、程序治理、Git 可 diff、本地优先、失败要具名」。
差别在**粒度与时间轴**：AOCI 是静态结构的一次性先验，我们是随会话演化的经验与边界。

**谁是权威**：如果同时用，必须分域，否则两个模型写的文本会互相漂移。建议边界——
**AOCI 是代码结构的权威，`MEMORY.md` 是项目事实与不变量的权威**；两边都不许摘要对方，
`/context export` 也不该把 AOCI 索引吞进去。

## 5. 值得借鉴 / 不适用

**借鉴三条（零新依赖）**

1. **交付证明**。我们的种子有「带了多少」（`continuationNotice`），但没有「模型确实读到了」的证明。
   AOCI 的 chunk + cursor + attestation 是重武器，我们只需要轻量版：种子落一个身份哈希，交接回执
   记下它，事后能对账「子会话读到的种子是不是这一份」。
2. **漂移词汇**。`Missing / Orphan / Stale / Unbaselined` 比我们 INDEX 对账里的「stranded / 未回填」
   更可操作；`Unbaselined`（有、但从未建立基线）尤其贴我们 `session-logs` 的补录场景。
3. **派生/权威标记**。它给所有投影挂 `derived=true`、`authoritative=false`；我们 `/context export`
   与 `/memory` 状态都是派生视图，回执里显式标一句「派生，权威是 journal」成本极低。

**不适用三条（都撞硬约束）**

1. **规模**：300K token 的索引在我们这里是灾难——157K 是质量膝线，桌面 profile 的交接线是 400K，
   读一次索引就把一个会话推到越线附近；而 dsh 的压缩会把它当历史摘要掉，AOCI 自己的规则也承认
   压缩后必须整份重载。
2. **依赖**：Go 单二进制 + stdio MCP 服务器 + 每仓初始化 1 小时/20 万行。我们四条流水线至今没有
   服务器、没有二进制；唯一的网络出口是宿主自己的模型调用。这个取舍不该为「代码理解」破例——
   那是宿主与子代理的职责。
3. **许可与分发**：FSL-1.1-MIT 是 source-available，不是 OSI；`dsh-aoci` 自己也不打包二进制，
   只校验 SHA-256。我们不可能把它塞进 npm 包。

## 6. DSH 侧现状：`dsh-aoci`

| 项 | 事实 |
|---|---|
| 版本 | `dsh-aoci@0.3.6`，npm 发布于 **2026-10-26**；仓库 commit `cf026a7` |
| 测试基线 | README 自述「DSH **0.2.0-rc.2**、cordis ^4.0.4」，web profile；36 个单测 |
| 工具面 | 九 MCP 工具 + 十余个确定性工具；`toolSurface: compact` 默认把九个折叠成
`aoci_overview` + `aoci_call` 一个聚合入口 |
| 桥接方式 | 动态 MCP 桥：`aoci --repo <root> mcp`，按需 spawn、sanitized env、2s 退避重连、unbind 注销 |
| 压缩协同 | 有 **compaction bridge**：把 AOCI 结果折进回执，按 `ctx.tokenMeter` 压力给
`fold` → `fold+compact` 建议（阈值 0.6/0.75/0.9） |
| 安全 | 二进制 SHA-256 + 最低版本校验；`readOnly` 关闭写入；`/aoci/api` 默认关 |
| 本机状态 | **未安装**（两个 profile 的 `cordis.patch.yml` 都没有 `dsh-aoci`），也没有 `aoci` 二进制 |

**兼容性风险**：它自测在 0.2.0-rc.2，本机宿主是 **0.2.2-rc.3**；我们自己的 API 基线是 0.1.7-rc.2、
peer 下限 `>=0.1.7-rc.2`。要用它，得先按 `dsh-version-upgrade-compat-probe` 那套重验一遍。
另外它是**同宿主内的第三方插件**，动态注册 MCP 工具会改模型可见的工具面——这和我们「不注册工具」
的现状是相反的选择。

## 7. 裁定与下一步（待拍板）

**建议裁定**：不引入为运行依赖；把 AOCI 当外部对照，而不是组件。

三个可选动作，按成本递增：

- **A. 只读试用（半天内）**：把 `linux_amd64` 资产下到 `/tmp`，复制本仓库到 `/tmp` 跑
  `aoci init` / `scan`，看两件事——索引的 token 规模、以及它对「`src/project-handoff/perform.ts` 为什么
  不能拆」这类约束写得好不好。**不碰本仓库、不装插件、不改配置。**
- **B. 若 A 有效再谈接入**：只作为「代码结构」维度的可选插件（`dsh-aoci`），与 `MEMORY.md` 明确分域，
  先跑兼容性重验；不做双写、不让它读我们的 memory 文档。
- **C. 无论 A/B 结果都值得做的借鉴**：种子身份哈希（对账「读到的是哪一份」）、INDEX 对账改用
  漂移分类词汇、回执标注「派生视图」。三条都是纯文本改动，不新增依赖。

**明确不做**：把 AOCI 索引塞进 `CONTEXT.md`/`MEMORY.md`；打包或镜像它的二进制；让两套写路径都写
「项目事实」；为了它改我们的交接阈值或压缩策略。

## 9. 证据清单与未解决项

**清单**：见 `.agents/evidence/2026-11-19-aoci/`（`manifest.tsv` 8 条，`failures.tsv` 4 条；
失败项包括 `r.jina.ai` / `github.com` 的 SSRF 拦截、arXiv API 空响应、research 工具被「时间戳」撞词污染）。

**未解决（写在这里，避免下次从零开始）**

1. **未实测**：索引质量、Linux 二进制行为、在 dsh 0.2.2-rc.3 上的插件兼容性——一条都没验。
2. **命名漂移未闭合**：论文的 "Code Indexing" 与仓库的 "Cognition Infrastructure" 是同一项目的两个阶段
   还是两个东西，README 没解释；引用时要分开写。
3. **规模结论待实测**：300K token 是 70 万行系统的数字；本仓库 `src/` 实测 19,552 行（测试另
   19,348 行），索引可能在几千 token 量级——「装不下」的结论在**本仓库**上未必成立，真要裁定，
   先用 A 方案量一次。
4. **与 dsh 原生能力的关系**：宿主已有子代理探索、`/context find`、以及未来的检索工具；AOCI 的
   「先验索引」是否比「按需检索」更省 token，在本仓库这种规模上没有证据。
